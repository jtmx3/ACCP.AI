# Conversation v3 — دليل Windows ونتائج التحقق

## النطاق

يعمل هذا التحديث على `feature/accp-natural-conversation-v3` انطلاقًا من commit المراجعة `5e314639112816320d987e33086265dbc62848aa`، ويضيف تفسيرًا غير حصري لأهداف الرسالة، وإحالات قابلة للتحقق، واستخراجًا مضبوطًا بالحقول، وإجابة إرشادية مستندة إلى مصادر محددة النطاق، مع إبقاء قرار السلامة والفرز والحفظ تحت سيطرة التطبيق. هذا نموذج تجريبي ببيانات اصطناعية، وليس خدمة طوارئ أو مشورة قانونية أو وسيلة لتقديم بلاغ. درجة الأولوية ليست احتمالًا ولا حكمًا على الواقعة.

يحافظ التنفيذ على SQLite والحفظ والاستكمال والتحقق من `expected_revision` وسجل الوقائع ومراجع المصدر والتصحيح والتأكيد المرتبط بإصدار التقرير. اقتراحات القواعد والنموذج لا تُفضّل لمجرد ترتيب التنفيذ: تُرفض الاقتراحات غير المسندة، وتُحفظ الخلافات الحقيقية كسجل توضيح، بينما تقيد علاقات المبالغ بقواعد الحدث. التصحيح المالي يبقى حدث تدقيق مستقلًا؛ لا يغيّر الحدث الأصلي أو اقتباسه ولا يخلق دفعة إضافية.

## التشغيل على Windows

افتح PowerShell من جذر المستودع، ثم جهز البيئة وشغّل التطبيق محليًا:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m pip install -r requirements-dev.txt
python -m app.rag --reindex
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

افتح <http://127.0.0.1:8000>. الافتراضي هو القواعد المحلية، ولا يحتاج مفتاحًا. لا تستخدم بيانات أشخاص حقيقيين ولا تعرض الخادم على شبكة عامة.

### Ollama المحلي

ثبّت Ollama وشغّله منفصلًا، مع الحفاظ على النموذج الذي يستخدمه صاحب المشروع دون تبديله:

```powershell
ollama --version
ollama pull qwen3.5:4b-q4_K_M
ollama list
```

في نافذة PowerShell نفسها التي ستبدأ منها التطبيق، اضبط التالي ثم أعد تشغيله:

```powershell
$env:MODEL_PROVIDER = "ollama"
$env:MODEL_BASE_URL = "http://127.0.0.1:11434/v1"
$env:MODEL_NAME = "qwen3.5:4b-q4_K_M"
$env:MODEL_TIMEOUT_SECONDS = "120"
$env:OLLAMA_REASONING_EFFORT = "none"
python -m app.rag --reindex
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

`OLLAMA_REASONING_EFFORT` إعداد Ollama مستقل؛ لا يغيّر إعداد المزود الخارجي. في لوحة **مسار التشغيل الفعلي** افحص الإعداد، واتصال الخدمة، وتوفر النموذج، ثم اختبر توليدًا ثابتًا. فحص القائمة لا يرسل نص حالة، واختبار التوليد يستخدم نصًا ثابتًا. لا يُعد ضبط المتغيرات دليل اتصال.

### تقييم v3 الاصطناعي باستخدام النموذج

الأداة التالية تجري أولًا فحص اتصال غير توليدي ومطابقة اسم النموذج، ثم اختبار توليد ثابت. بعد نجاحهما فقط ترسل أدوار مجموعة v3 الاصطناعية الثابتة إلى المزود. إذا فشل أي فحص تحفظ حالة `not_run` دون ادعاء نتيجة نموذج. الأمر الافتراضي لا يرسل السياق السابق؛ `--with-context` اختيار منفصل لإجراء اختبار سياق اصطناعي محدود، ولا يرسل أي جلسة مستخدم:

```powershell
python -m scripts.evaluate_conversation_v3 `
  --mode model `
  --suite tests/conversation_v3_acceptance_reviewed.json `
  --output reports/evaluation/conversation-v3-model-windows.json
```

لاختبار حدود السياق بموافقة صريحة منفصلة في مجموعة اصطناعية فقط، أضف `--with-context` إلى الأمر. استخدم اسم ملف إخراج جديدًا لكل تشغيل. سجّل زمن طلب النموذج، والحقائق المقبولة في اختبار الاستخراج المنفصل، والمعلومات الصحيحة التي أُغفلت أو الحقول المحظورة المقترحة، ونتيجة دمج API، والرجوع للقواعد. نجاح المسار المتكامل أو fallback لا يُسجل نجاحًا لاستخراج النموذج. لا تُعامل استجابة JSON صالحة أو `valid_empty` على أنها استخراج صحيح.

تقييم القواعد المستقل لا يستدعي نموذجًا:

```powershell
python -m scripts.evaluate_conversation_v3 `
  --mode rules `
  --suite tests/conversation_v3_acceptance_reviewed.json `
  --output reports/evaluation/conversation-v3-rules-windows.json
```

في الواجهة، إرسال نص الرسالة الحالية للنموذج يحتاج موافقة مستقلة لكل رسالة؛ وإرسال سياق سابق يحتاج موافقة أخرى اختيارية منفصلة، وكلاهما غير محدد افتراضيًا. سياق الاستخراج محدود بعدد الرسائل والحقائق والأحداث وحد أقصى 4500 حرف؛ لا يرسل السجل الكامل أو رمز الجلسة. إجابة الإرشاد تستخدم مسار موافقة مستقلًا ومقتطفات محلية منتقاة. خطر مباشر صريح يُفحص محليًا قبل انتظار النموذج أو الاسترجاع. أداة التقييم ترسل حالات اصطناعية منشورة في المستودع فقط.

## النتائج القابلة لإعادة الإنتاج

### قبل التعديلات

شُغّل evaluator v3 على commit الأساس `5e314639` في worktree مؤقت، دون تعديل التطبيق في ذلك المرجع. على المجموعة المقارنة ذات 20 حالة (18 حالة من نسخة المراجعة و2 استكماليتين) اجتاز النظام **4/20 حالة** و**49/85 تحققًا** قبل الإصلاح. الملف الخام: [`conversation-v3-rules-20-before-v2-base-2026-11-06.json`](../reports/evaluation/conversation-v3-rules-20-before-v2-base-2026-11-06.json). الحالتان الإضافيتان كُتبت توقعاتهما بعد التنفيذ الأول وقبل تقييمهما، لذا ليستا مجموعة عمياء.

أما المجموعة الأصلية المجمدة حرفيًا ذات 18 حالة، فقد اجتاز الأساس **3/18** و**43/76**؛ ملفها محفوظ منفصلًا: [`conversation-v3-rules-before-v2-base-2026-11-06.json`](../reports/evaluation/conversation-v3-rules-before-v2-base-2026-11-06.json).

### بعد التعديلات

على نسخة المراجعة الاصطناعية ذات 18 حالة: اجتازت القواعد **18/18 حالة، 81/81 تحققًا**، وكانت صلة الإجابات والمصادر **14/14**. الملف النهائي: [`conversation-v3-rules-reviewed-final-2026-11-06.json`](../reports/evaluation/conversation-v3-rules-reviewed-final-2026-11-06.json). وعلى مجموعة العشرين (18 مراجعة + حالتان استكشافيتان موضحتان أعلاه) اجتازت القواعد **20/20 حالة و85/85 تحققًا**، ونجحت إحالات الإرشاد **18/18**. زمن أدوارها المحلي P50 **8.1 ms** وP95 **13.1 ms**. التقرير: [`conversation-v3-rules-20-final-2026-11-06.json`](../reports/evaluation/conversation-v3-rules-20-final-2026-11-06.json). هذه نتائج للقواعد والمسار المتكامل، لا للنموذج.

المجموعة الأصلية بقيت حرفيًا دون تغيير في [`conversation_v3_acceptance.json`](../tests/conversation_v3_acceptance.json). النتيجة الحالية **14/18 حالة و71/76 تحققًا**؛ وإخفاقاتها الأربعة ظاهرة في [`conversation-v3-rules-frozen-final-2026-11-06.json`](../reports/evaluation/conversation-v3-rules-frozen-final-2026-11-06.json): Q06 يتوقع حدثًا ماليًا واحدًا رغم وجود طلب وتحويل؛ Q10 وQ15 لا يحسبان سجل التصحيح الإضافي؛ وQ14 يجيب «نعم» قبل تقديم تفاصيل/وقت الواقعة والوصول فعلًا إلى سؤال التكرار. لم نغيّر هذه التوقعات. توجد نسخة مراجعة منفصلة تستدرك هذه العيوب المحددة في fixtures، ومقاييسها معروضة أعلاه.

لم يُشغّل تقييم استخراج حي في تسليم v3.1: البيئة كانت مضبوطة على `rules`، لذلك فشل الفحص المسبق بأمان، ولم يُرسل أي دور من المحادثة إلى مزود؛ التفاصيل التاريخية: [`conversation-v3-model-not-run-2026-11-06.json`](../reports/evaluation/conversation-v3-model-not-run-2026-11-06.json). أما فحوص متابعة v3.2 ونتائجها النهائية فترد في القسم التالي. لم نختبر Windows أو Ollama فعليًا في هذا التنفيذ.

كل هذه الحالات مولدة اصطناعيًا وليست مراجعة بشرية مستقلة، ومجموعة صغيرة لا تثبت تعميمًا أو دقة استخدام واقعي. إدراج حالات holdout معروفة في اختبارات الانحدار لا يجعلها غير مرئية أو مستقلة.

## ما لم يُختبر

في تسليم v3.1 كان التطبيق مضبوطًا على `MODEL_PROVIDER=rules`، لذلك لم يُتحقق من اتصال خدمة Ollama أو توفر `qwen3.5:4b-q4_K_M`، ولم يُجر تقييم استخراج حي أو تجربة Windows فعلية؛ موائم HTTP الوهمي يختبر سلوك الكود فقط. يُترك التحقق الحي لصاحب المشروع عبر أمر PowerShell أدناه، وتُحفظ النتيجة الفعلية في ملف مستقل. كذلك لا تثبت التجارب الاصطناعية صلاحية فرز قانوني، أو تغطية كل اللهجات، أو الجاهزية للبيانات الواقعية.

## متابعة v3.2 — إصلاحات مراجعة commit `76c2966b`

أُجريت هذه المتابعة على الفرع `feature/accp-natural-conversation-v3` دون تعديل توقعات مجموعات التقييم الأصلية أو دمج أي PR. يقيّد مدقق النموذج الآن إحالة الحدث المالي بنوع الحقل والعملية والحالة والقيمة، ويمنع استخدام حدث دفع لإسناد هوية أو تغيير المبلغ/العملة تحت عبارة «نفس الدفعة». لا يصل اقتراح غير مسند إلى الدمج. اختبارات API تتحقق من أن الاسم المختلق لا يظهر في الحالة أو التقرير أو JSON، مع قبول الإحالات المالية المطابقة.

تتضمن نتيجة الفهم المنظمة خطة أهداف الرسالة والوقائع المقبولة والتشخيص. يستخدم التوجيه خطة الأهداف بعد التحقق، تحت القرار النهائي للتطبيق؛ لذلك يمكن قبول طلب إرشاد مع `facts=[]` من دون اختراع وقائع أو إعادة سؤال وصف الواقعة. أضيفت اختبارات لطلب إرشاد غير مصاغ كسؤال محفوظ ولرسالة تجمع معلومة وطلب نصيحة. وفي السؤال المختلط عن سبب الدرجة، تُحفظ نية التفسير قبل متابعة تسجيل الوقائع، فيُشرح التقييم بدل إعادة سؤال الدفع.

سلسلة تصحيحات المبلغ تربط كل تصحيح بالحدث الأصلي، وتشتق القيمة الحالية من آخر تصحيح. يطابق اختيار الهدف الرقم والعملة، ويُطلب توضيح عند تعدد الأهداف المحتملة. سجل التصحيح لا يُحسب دفعة أو طلبًا إضافيًا، ويبقى المدفوع مستقلًا. أضيفت تغطية لثلاثة تصحيحات متتابعة، وتصحيح حدث أقدم مع أحداث أحدث، والتصحيح الملتبس، والاستمرار والحفظ وتصدير JSON وMarkdown وعرض المتصفح مع إبقاء الاقتباس الأصلي حرفيًا.

## تعريف المقاييس ومقاماتها في `conversation-v3-2`

`model_eligible_turns` هو عدد أدوار المستخدم المؤهلة لمحاولة استخراج النموذج في المجموعة؛ يُستبعد السؤال الواضح محليًا وحالات الخطر ومسارات غير الاستخراج. `provider_attempts` هو عدد استدعاءات المزود التي بدأت فعليًا، بعد الفحص المسبق. معدل الرجوع `provider_fallback_rate` مقامه الأدوار المؤهلة، وبسطه عدد الأدوار التي أعاد فيها مسار API فعلًا `fallback_used=true`؛ لا يُستنتج من تتبع النموذج وحده.

`provider_accepted_responses` يعد الردود التي قبلها مدقق الاستخراج بنيويًا، بما فيها رد صحيح بلا وقائع (`valid_empty`) أو رد صفّى المدقق كل مقترحاته. هذا **ليس** نجاح استخراج. `provider_rejected_responses` يعد الردود المستلمة التي رفضها مدقق البنية أو الوقائع؛ لا يدخل فيه انقطاع الاتصال أو خطأ HTTP أو غياب الرد. تعرض `provider_fallback_categories` أسباب الرجوع منفصلة، مثل فشل الاتصال، وخطأ HTTP، والرد الفارغ من المزود، ورفض الرد، والاستخراج الصالح بلا حقائق، وتصفية كل الحقائق، وفشل المزود.

`provider_extractions_with_accepted_facts` يعد الاستدعاءات التي قبل المدقق فيها حقيقة واحدة على الأقل، ومقام نسبة التغطية الاختبارية للنموذج هو `model_extraction_only.expected_fact_checks` (حقول الاستخراج المؤهلة فقط، لا حقول السلامة والقرار التي يديرها المحرك). `provider_accepted_fact_count` هو مجموع الوقائع التي اجتازت المدقق. لا يثبت نجاح المسار المتكامل نجاح الاستخراج وحده، ولا يُحسب الرجوع للقواعد نجاحًا للنموذج.

`accepted_fact_merge_dispositions` يعد مقترحات الوقائع المقبولة بحسب قرار الدمج. وتفصل الحقول الإضافية بين ما تجاهله الدمج، وما أحاله إلى محلل القواعد المالي، وما سجله كتعارض للمستخدم، وما سجله كتعديل. هذه الأعداد مقاماتها وقائع النموذج المقبولة التي لها أثر دمج مسجل، لا عدد المحادثات. `turns_with_accepted_facts_ignored_by_merge` يعد الأدوار التي تجاهل فيها الدمج حقيقة مقبولة واحدة على الأقل.

زمن المزود هو زمن طلب HTTP المقاس داخل العميل. `model_pipeline_elapsed` يشمل الطلب والتحقق. زمن التكامل يقيس معالجة API والدمج بعد إدخال استخراج النموذج المحقون في المقيّم، و`turn_total_elapsed` هو مجموع خط النموذج وزمن التكامل؛ تعرض أزمنة P50 وP95 كلًا على حدة. في وضع القواعد يكون زمن المزود غير منطبقًا.

## نتائج هذه المتابعة

على Linux/Python 3.12، نجحت مجموعة الاختبارات الكاملة **143/143** مع `ResourceWarning` كأخطاء؛ تشمل ذلك اختبارات التخزين وAPI والتزامن والمتصفح والانحدارات الجديدة. واجتاز أيضًا `git diff --check` وفحص تركيب Python؛ لم يُنفّذ هذا الفحص على Windows.

اجتازت مجموعة المراجعة الاصطناعية المنفصلة **18/18 حالة و81/81 تحققًا** في [التقرير النهائي v3.2](../reports/evaluation/conversation-v3-2-rules-reviewed-final-2026-11-06.json). واجتازت مجموعة العشرين الاصطناعية **20/20 حالة و85/85 تحققًا** في [تقرير v3.2 للعشرين](../reports/evaluation/conversation-v3-2-rules-20-final-2026-11-06.json). بقيت المجموعة المجمدة الأصلية وتوقعاتها كما هي: **14/18 حالة و71/76 تحققًا**، وتفاصيلها في [التقرير المجمد v3.2](../reports/evaluation/conversation-v3-2-rules-frozen-final-2026-11-06.json). عادت أداة التقييم برمز إخفاق لهذه المجموعة لأن الحالات الأربع غير ناجحة؛ لم أعدّل التوقعات لإخفاء ذلك.

لم تُجرَ تجربة Ollama حية هنا. كان الإعداد الفعلي `MODEL_PROVIDER=rules`؛ فشل الفحص المسبق بالسبب `not_configured`، مع **صفر محاولات** وصفر أدوار نموذج، ولم يُرسل أي نص إلى مزود. هذا ليس دليلًا على أن Ollama غير متاح على جهاز Windows، ولا نتيجة تقييم نموذج. سجل الفحص في [تقرير عدم التشغيل v3.2](../reports/evaluation/conversation-v3-2-model-not-run-2026-11-06.json). لا تزال تجربة Windows الحية المطلوبة معلّقة عند صاحب المشروع.


## أمثلة قبل الإصلاح وبعده

- **إحالة دفعة لاختلاق هوية:** قبل الإصلاح أمكن أن تُحفظ `identity=reported, value=أحمد` من اقتباس «نفس الدفعة» مع مرجع حدث `paid=130 دينار`. بعده يعطي المدقق `facts=[]` ورمز `context_reference_invalid`. يثبت اختبار API أن `أحمد` غير موجود في `session.facts` أو التقرير أو تنزيل JSON؛ تبقى الوقائع المالية المسجلة أصلًا كما هي، ويستمر الحوار عبر توجيه التطبيق والقواعد لا عبر الهوية المختلقة.
- **طلب نصيحة أثناء سؤال الوصف:** قبل الإصلاح كانت الخطة المقبولة `ask_guidance` مع `facts=[]` تُهمل ويُعاد سؤال وصف الواقعة. بعده يسجل رد API `question_detected=true` ويستدعي مسار الإرشاد المحلي مرة واحدة، ويعرض خطوات النصيحة، ولا ينشئ حقيقة من «بدي نصيحة» ولا يزيل السؤال المعلّق عن الواقعة. وفي الرسالة المختلطة تُحفظ لقطات الشاشة ويُجاب عن النصيحة في الدور نفسه.
- **ثلاثة تصحيحات للمطلوب:** بعد الإفادة «طلب مني 100 دينار وحولت 130 دينار بالمحفظة» ثم تصحيحات 120 و140 و160، تعرض الحالة المحفوظة `requested_amount=160 دينار` و`paid_amount=130 دينار`. كل سجلات التصحيح الثلاثة تشير إلى `money-1` وتحتفظ بالقيم السابقة 100 ثم 120 ثم 140. يعرض JSON القيمة الحالية للحدث الأصلي 160، ويعرض Markdown سجل التدقيق من دون عدّه طلبًا أو دفعة جديدة؛ يبقى الاقتباس الأصلي حرفيًا.
- **سؤال سبب التقييم مع إفادة دفع:** قبل الإصلاح كان التطبيق يسجل 130 دينار ثم يجيب بسؤال تمييز المبلغ المطلوب والمدفوع. بعده يسجل 130، ويشرح `90/100` والخطر المباشر المسجل كمنفي، ثم يتابع من خانة المقابلة المناسبة. هذه أمثلة اختبارات اصطناعية بمزود وهمي أو قواعد محلية، وليست تشغيلًا حيًا للنموذج.


## متابعة v3.3 — صلة إرشادات الحساب بالمنصة

- `fact_field_status_value_accuracy`: عدد الحقول المقبولة الصحيحة في الحالة والقيمة على `scored_expected_fact_count`، أي الحقائق المتوقعة في الاستجابات المقبولة بنيويًا. `fact_field_status_value_end_to_end_coverage` يقسم المطابقات نفسها على **كل** الحقائق المتوقعة، بما فيها حالات الرد المرفوض أو عدم الاستجابة؛ ويبقى `unscored_expected_fact_count` ظاهرًا لتفسير ذلك.
- `fact_quote_accuracy`: الاقتباسات المطابقة حرفيًا على الحقائق المتوقعة القابلة للتقييم. `fact_field_full_status_value_quote_coverage` يطلب مطابقة الحالة والقيمة والاقتباس معًا، ومقامه كل الحقائق المتوقعة. `accepted_fact_exact_match_precision` يقيس دقة الحالة والقيمة بين الحقائق التي اجتازت المدقق؛ و`accepted_fact_full_match_precision` يضيف تطابق الاقتباس.
- الإغفال (`omitted_fields`)، والتصفية (`filtered_expected_fields` و`filtered_proposals_by_code`)، والحقائق الإضافية المقبولة، والاستجابة المرفوضة، والاستجابة الصالحة بلا حقائق (`valid_empty`) حالات منفصلة؛ لا يُملأ أي منها من القواعد.
- `model_raw_output` يحفظ بصمة استجابة المزود وحجمها والمقترحات المنظمة كما صدرت قبل التحقق، منفصلة عن `validator_accepted_facts` و`validator_filtered_proposals`. لا يحفظ جسم الرد الخام الكامل. `application_normalizations` فارغ في هذا الاختبار؛ لا يجري إصلاح أو دمج في المشغل.
- `request_body_bytes` و`prompt_char_count` و`model_response_bytes` أحجام منفصلة. `provider_latency_ms` زمن استدعاء النموذج، و`total_elapsed_ms` يشمل التحقق المحلي. `provider_attempt_count` عدد استدعاءات استخراج النموذج، مع زمن الفحص المسبق منفصلًا؛ المقام المتوقع في تشغيل كامل دون إعادة محاولة هو محاولة واحدة لكل حالة. لا تعد المقاييس fallback أو نجاح المحادثة المتكاملة نجاحًا للنموذج.

## متابعة v3.4.3 — حفظ دقة الساعة في deadline

بعد إصلاح `18f84c6` أظهرت اختبارات المدقق الاصطناعية أن `6:30` و`6:45` و`6` و`6 صباحًا/مساءً` أمكن اختزالها إلى توقيع واحد. السبب أن تنظيف علامات الترقيم كان يحذف النقطتين، ونمط الساعة كان يتوقع `ساعه` بينما النص المطبّع يبقي التاء المربوطة في «الساعة»؛ لذلك كان التحليل يلتقط رقم الساعة وحده.

## متابعة v3.4.5 — نفي محصور بالمجال، أهداف خام، واقتباسات مسندة

تُعالج هذه المتابعة أخطاء مثبتة في تقرير Windows الذي قدّمه صاحب المشروع. في المدقق، رُبط فحص النفي وعدم المعرفة بالعبارة والحقل المعنيين: اقتراح `published=true` بعد «ما حصل نشر لصور الحساب»، و`threat=true` بعد «ما صار أي تهديد مباشر»، و`paid_amount/unknown` بعد «ما دفعت أي مبلغ» تُصفّى الآن بأسبابها؛ ولا يصبح غياب الرقم وحده دليلًا على `unknown`. أُضيف اختبار API يمر عبر الاستخراج والمدقق الفعليين مع ردود مزود اصطناعية، ويتحقق من أن المقترحات الثلاثة لا تصل إلى الحالة أو التقرير، مع بيان أن قرار المدقق المنفصل يتبعه fallback القواعد ولا يُنسب نجاحه إلى النموذج.

قُصّر عقد البرومبت مع أمثلة JSON مباشرة للحالات `denied/unknown/not_remembered/declined`، والقيمة الثنائية `false` مقابل `null` النصية/الزمنية/المالية، وإجابة السؤال المعلّق مع طلب إرشاد في الرسالة نفسها. `guidance_question` يجب أن يكون مقطعًا حرفيًا من طلب إرشاد فعلي؛ وقيم `deadline` يجب أن تبقى مقاطع حرفية بلغة السند، مع المحافظة على الاتجاه والساعة والإزاحة. المدقق يرفض القيمة المترجمة أو المعاد صياغتها ولا يصلحها بصمت.

### إصدار القياس 3.0

بقيت المجموعة الأصلية `tests/extraction_contrastive_v1.json` ومجموعة المتابعة وتوقعاتهما دون تغيير. رُفع `scoring_version` إلى `3.0` لأن المقاييس وبوابة النجاح تغيرت، وبقيت تقارير الإصدارات السابقة دون استبدال. مقاييس الاقتباس الجديدة ومقاماتها:

- `fixture_exact_quote_coverage`: اقتباس مقترح يطابق نص الـfixture حرفيًا، مقسومًا على **كل الحقول المتوقعة**؛ الحقل المغفَل يُحسب غير مطابق.
- `literal_source_span_coverage`: اقتباس مقترح يظهر حرفيًا كجزء غير فارغ من رسالة المستخدم الحالية، مقسومًا على **كل الحقول المتوقعة**.
- `grounded_quote_field_status_value_coverage`: عدد اقتباسات الحقول المتوقعة التي يقبل المدقق الحقيقي معها الحقل والحالة والقيمة، مقسومًا على **كل الحقول المتوقعة**. يختبر التقرير كل اقتراح منفردًا دون دمج أو fallback.
- `grounded_quote_proposal_precision`: الاقتراحات المسندة المقبولة بالمدقق، مقسومة على **عدد الحقول المتوقعة التي قدم النموذج لها اقتباسًا**.
- `accepted_expected_fact_grounded_precision`: حقائق الحقول المتوقعة المقبولة المطابقة للحالة/القيمة والمدعومة بالاقتباس، مقسومة على **حقائق الحقول المتوقعة المقبولة**.
- `fact_quote_accuracy` و`accepted_fact_full_match_precision` القديمان يبقيان للمقارنة التاريخية على أساس التطابق الحرفي مع نص fixture، لكنهما لم يعودا بوابة لصحة الاقتباس. لا يُعد اختلاف نقطة أو اقتباس أطول حرفي صحيح اختلاقًا للسند.

تُسجل أهداف النموذج الخام المنظّمة داخل `goals.raw_model_output` و`model_raw_output.message_goals` حتى عند رفض الاستجابة، وتُفصل عن `validator_accepted_goals` و`validator_unsupported_goals`. `raw_goal_exact_case_matches` مقامه **الحالات التي تضمنت قائمة message_goals منظمة قابلة للقياس**؛ ودقتا/استدعاء الهدف الخام مقامهما الإيجابيات/التنبؤات الخام، بما في ذلك الردود المرفوضة التي بقيت فيها أهداف JSON قابلة للقراءة. أما المقاييس القديمة `goal_*` فتخص الاستجابات المقبولة فقط. بوابة الإصدار 3.0 تشترط اكتمال التقييم وعدم وجود رد غير صالح أو حقيقة غير مقاسة، وتطابق الأهداف الخام، وتغطية جميع حقائق الحقول المتوقعة بقيمة/حالة صحيحتين واقتباس يقبله المدقق؛ ولا تشترط التطابق النصي مع عبارة fixture. هذه بوابة تقييم الاستخراج، لا قياس نجاح النظام المتكامل.

## متابعة v3.4.6 — إسناد النفي إلى الفعل

أعاد صاحب المشروع إنتاج خطأ في المدقق على commit `bca3d5b`: في «ما نشر الصور وهددني بنشرها» عُمّم نفي النشر خطأً على التهديد؛ وفي «ما بعرف مين هددني» عُمّم عدم معرفة هوية الشخص على وقوع التهديد. السبب أن اختبار وجود علامة النفي/الجهل ومرساة الحقل داخل الجملة أو الشطر نفسه لم يثبت أن العلامة تتعلق بفعل ذلك الحقل.

أضيف تحليل موضعي محافظ لظهور الأفعال في حقلي `threat` و`published`. يقيس النفي قبل الفعل المعني، ولا ينقل نفي الفعل الأول عبر واو عطف إيجابية إلى الفعل التالي. ويتعرف على `ولا` بوصفها نفيًا منسقًا للفعل اللاحق في «ما هددني ولا نشر الصور». كما لا يعد «بنشرها» بعد فعل تهديد واقعة نشر فعلية. في «ما بعرف مين هددني» يُسند الجهل إلى هوية الفاعل لا وقوع التهديد؛ أما «ما بعرف إذا هددني» فتبقى حالة جهل بوقوع التهديد. عند غياب سند واضح تُصفّى الحالة برمز التحقق بدل تحويلها إلى حالة أخرى بصمت.

أضيفت اختبارات للقبول والرفض مع اقتباس الرسالة كاملة أو مقطع صحيح منها، وللنفي المنسق بـ«ولا»، ولجهل هوية الفاعل مقابل جهل وقوع التهديد. وُسّع اختبار API القائم ليتحقق من تصفية `threat/denied/false` الخاطئة قبل حفظها، مع فصل نتيجة المدقق عن الرجوع للقواعد.

نتيجة التحقق على Linux/Python 3.12.3: **236/236 اختبارًا ناجحًا** مع `ResourceWarning` كأخطاء خلال 25.511 ثانية، ونجحت فحوص JavaScript وPython و`git diff --check`. لا تغيّر هذه المتابعة البرومبت أو مجموعات التقييم/تقاريرها التاريخية، ولم يُشغّل Ollama أو يُقَس تحسن حي؛ الحالات والردود الاصطناعية تثبت سلوك المدقق فقط.
